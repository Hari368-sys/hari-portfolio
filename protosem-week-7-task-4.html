Firebase IoT Monitoring Dashboard

Monitor temperature, humidity and light in a login-protected Firebase dashboard and control a bulb.

← Week 7Task 1Task 2Task 3Task 4Task 5

01Overview

The ESP32 reads temperature, humidity and light level and pushes the readings to a Firebase Realtime Database. A web dashboard, protected by a login, shows the live values and lets the user switch a bulb through a relay.

02Concepts

Firebase Realtime Database

A cloud database that syncs data to every connected client in real time. The ESP32 writes sensor values and reads the bulb command.

Firebase Authentication

Email and password login, so only a signed-in user can see the dashboard or control the bulb.

Two-way data

Sensor data flows from the ESP32 to the dashboard; the bulb command flows from the dashboard back to the ESP32.

03System Design

Sensors→ESP32→Firebase database→Login dashboard→Relay and bulb

04Hardware & Software

Hardware

  • ESP32 development board
  • DHT11 temperature and humidity sensor
  • LDR with a fixed resistor (light sensor)
  • Relay module and bulb with holder

Software & platforms

  • Arduino IDE
  • Firebase project (Realtime Database and Authentication)
  • Firebase ESP32 client library, DHT library
  • Web dashboard (HTML, CSS and JavaScript)
  • Firebase Hosting, to publish the dashboard on a web.app address
  • Node.js, needed for the Firebase tools

07Configuration

  1. Install the Firebase tools with npm install -g firebase-tools, check them with firebase --version and sign in with firebase login
  2. Create a Firebase project and enable Realtime Database
  3. Enable Email/Password authentication and add a user
  4. Set the database rules so only signed-in users can read or write the sensors, control, logs and status data (logs are indexed on the timestamp)
  5. Copy the API key and database URL into the sketch and dashboard
  6. Publish the dashboard pages: in the project folder run firebase init hosting, choose Use an existing project, select iot-smart-system-fd89c and use . as the public directory, keeping the existing index.html
  7. Run firebase deploy to release the site to the Hosting URL

09Challenges & Fixes

  • Dozens of npm warnings during the Firebase tools install. Running npm install -g firebase-tools printed a long list of “deprecated” warnings and an install-scripts notice, which looked like the install had failed. It had not: the install finished with “added 672 packages”, and firebase --version returned 15.30.0. Checking the version after the install, instead of judging by the warnings, was the quick way to confirm the tools were ready.
  • Hosting setup offered to overwrite my login page. While running firebase init hosting, Firebase found that an index.html already existed in the project folder and asked whether to overwrite it. I answered No, so my own login page was kept and only 404.html, firebase.json and .firebaserc were added. The public directory was set to . so that index.html and dashboard.html are deployed together.
  • Keeping the database private. A Realtime Database that anyone can read or write is not safe for a project that switches a bulb. I wrote the rules so the sensors, control, logs and status nodes can only be read or written when auth != null, and added an index on timestamp for the logs. Only a signed-in user can see readings or send a command.
  • The dashboard showing “Waiting for data…”. After logging in, the cards showed “0 readings loaded” and the Realtime Database data tab showed null. Nothing has been written to the database yet: the dashboard only displays what the ESP32 pushes. Opening the Data tab in the Firebase console showed me quickly that the dashboard itself was loading fine and the database was simply empty.

10Reflection

This task moved the project from a device that I control to a service that other people could sign in to. In Tasks 1 to 3 the only question was whether the bulb switched. Here I also had to ask who is allowed to see the readings and who is allowed to send a command, which is why Firebase Authentication and the database rules mattered as much as the dashboard itself. Seeing the database rules require a signed-in user for every node made the idea of access control much more concrete than reading about it.

It also showed me how many separate pieces a “simple” cloud dashboard has: the Firebase project, the database, the sign-in method, the web pages, and Firebase Hosting to publish them. When the dashboard said “Waiting for data”, I could check each piece one by one in the console instead of guessing. The next step is to connect the ESP32 so it writes live temperature, humidity and light readings, so that the trend charts and the CSV export have real data to show.
